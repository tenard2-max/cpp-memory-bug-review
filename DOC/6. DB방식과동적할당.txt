# 추가 개발 요건서: 사전 인덱스 + 동적 Context Injection 기반 `.cpp` 검증 파이프라인

| 항목 | 내용 |
|---|---|
| 문서 종류 | Addendum (기존 `llm_gateway_requirements.md` 의 추가 요건) |
| 문서 버전 | v1.0 |
| 작성일 | 2026-10-26 |
| 개발 도구 | Cursor |
| 선행 조건 | 보안 게이트웨이(인증/승인/감사 로그) 구현 완료 후 LLM 호출 경로에 연결 |

---

## 1. 배경 및 목표

### 1.1 문제
현재 LLM 검증 속도가 느린 주된 원인은 **프롬프트가 불필요하게 길기 때문**이다. 레거시 코드는 헤더와 매크로 의존이 많아, 관련 정의를 모두 넣으면 입력 토큰이 수만 개에 달하고, LLM 추론 시간(특히 Prefill 단계)이 길어진다.

### 1.2 목표
- **G-1**: `.cpp` 파일 검증에 필요한 헤더·구조체·매크로만 선별하여 **입력 토큰을 최소화**한다.
- **G-2**: 선별 과정(의존성 추출 + 벡터 검색)은 **사전 인덱스 조회로 1초 이내**에 끝낸다. (0.1초 목표는 벡터 검색 단독 기준으로 적용하며, 전체 체감 지연은 LLM 단계가 좌우한다.)
- **G-3**: LLM 출력은 **근거(라인 번호, 심볼)를 자동 검증**하여, 실제 코드에 없는 지적은 환각으로 간주하고 별도 표시한다.
- **G-4**: 모든 LLM 호출은 기존 보안 게이트웨이를 경유한다.

### 1.3 성능 목표 (벤치마크 후 확정)

| 항목 | 목표 |
|---|---|
| 의존성 추출 + 컨텍스트 선별 | 1초 이내 (파일 1,000줄 기준) |
| 벡터 검색 단독 | 0.1초 이내 (Top-K=20 기준) |
| 입력 프롬프트 크기 | 전체 헤더 투입 방식 대비 80% 이상 감소 |
| 파일 1개 End-to-End 검증 | 30초 이내 (7B 모델, 1,000줄 기준, 목표치) |

## 2. 전체 아키텍처

```
[Phase 1: Index — 최초 1회 / 헤더 변경 시]
 .h 파일, 매크로, struct/class/enum/typedef, 전역 선언
        │
        ▼
 Parser (tree-sitter-cpp) → Semantic Chunk 생성
        │
        ├─ Vector Store (FAISS 또는 Chroma)  : 임베딩 벡터
        └─ Symbol Store (SQLite)             : 심볼명 → chunk 역인덱스 (정확 매칭)

[Phase 2: Execute — UI에서 .cpp 선택 시]
 .cpp 선택
   │
   ▼
 Step 1  파싱 (tree-sitter)
   │
   ▼
 Step 2  사용 심볼 추출 (함수 호출, 타입, 전역변수, 매크로)
   │
   ▼
 Step 3  Context 선별
          ├─ 3-1 Symbol Store 정확 매칭 (1차)
          ├─ 3-2 미해결 심볼 벡터 검색 (2차 보완)
          ├─ 3-3 의존 확장 (선택된 struct가 참조하는 타입, depth ≤ 2)
          └─ 3-4 토큰 예산 내 우선순위 절삭
   │
   ▼
 Step 4  프롬프트 조립 → Security Gateway → Ollama (Qwen 등)
   │
   ▼
 Step 5  출력 파싱 → 후검증(Post-validation) → UI 리포트
```

## 3. Phase 1: Index 요구사항

### 3.1 대상 수집
- **IDX-01** 다음 정의를 인덱싱 대상으로 한다.
  - 매크로 (`#define` 상수형, 함수형)
  - `struct`, `class`, `union`, `enum`, `typedef`, `using` 별칭
  - 함수 선언 (헤더의 프로토타입)
  - `extern` 전역 변수 선언
  - 네임스페이스 및 static 상수 (`constexpr`, `const`)
- **IDX-02** 헤더 내부의 **함수 본문(inline 구현 포함)** 은 기본적으로 제외한다. 설정으로 포함 여부를 선택할 수 있어야 한다.
- **IDX-03** 대상 디렉토리는 `config/index.yaml` 에 나열한다. (예: `include/`, `common/`, `legacy/**/*.h`)

### 3.2 파싱 방식
- **IDX-04** 파서는 **tree-sitter-cpp** 를 사용한다. 정규식으로 struct/매크로를 추출하는 방식은 금지한다 (중첩 구조, 템플릿, 여러 줄 매크로에서 오류 발생).
- **IDX-05** 매크로 처리
  - `#define` 은 원문 그대로 chunk로 보존하고, 조건부 컴파일(`#ifdef`, `#if`)은 **빌드 설정의 정의값**을 기준으로 분기한다.
  - 빌드 설정 소스: `compile_commands.json` (권장) 또는 `config/defines.yaml`
  - 정의되지 않은 조건 분기는 **두 분기 모두 인덱싱**하고 `condition` 메타데이터로 표시한다.
- **IDX-06** `#include` 그래프를 생성하여 헤더 간 의존 관계를 `include_edges` 테이블에 저장한다.

### 3.3 Semantic Chunk 규격
- **IDX-07** 청크 단위는 **심볼 1개 = 청크 1개** 를 원칙으로 한다. 큰 구조체(예: 200줄 이상)는 필드 단위로 분할하되 `symbol_name` 은 유지한다.
- **IDX-08** 각 청크는 다음 메타데이터를 가진다.

| 필드 | 설명 |
|---|---|
| chunk_id | 고유 ID (해시 기반) |
| kind | macro / struct / class / enum / typedef / function_decl / global_decl |
| symbol_name | 심볼 이름 (정확 매칭 키) |
| file_path | 원본 헤더 경로 |
| line_start, line_end | 원본 라인 범위 |
| dependencies | 이 청크가 참조하는 다른 심볼 목록 |
| condition | 조건부 컴파일 조건 (없으면 null) |
| file_hash | 원본 파일 해시 (증분 갱신용) |
| text | 청크 원문 |

- **IDX-09** 임베딩 입력 텍스트는 `kind + symbol_name + 원문` 을 결합하여 생성한다 (심볼명 포함 시 검색 정확도 향상).

### 3.4 임베딩 및 저장
- **IDX-10** 임베딩 모델은 **로컬 실행 가능한 모델**을 사용한다. 한글 주석이 섞인 코드를 고려하여 다국어 모델을 기본으로 한다 (예: `bge-m3`, `multilingual-e5-base` 중 벤치마크 후 선택).
- **IDX-11** 벡터 저장소는 **FAISS**(파일 기반, 단일 서버 환경 권장) 또는 **Chroma**(영구 저장 옵션) 중 선택하며, 저장 경로는 설정 파일에서 지정한다.
- **IDX-12** Symbol Store(SQLite)에 `symbol_name → chunk_id` 역인덱스를 반드시 구축한다. 정확 매칭은 벡터 검색보다 우선한다.
- **IDX-13** 인덱스 파일과 DB는 **영구 저장**하며, 재기동 시 재인덱싱 없이 로드한다.

### 3.5 증분 갱신
- **IDX-14** 인덱싱 시 각 헤더의 SHA-256 해시를 저장하고, 재실행 시 변경된 파일만 재처리한다.
- **IDX-15** 헤더가 변경되면 **그 헤더를 include 하는 모든 .cpp 의 검증 캐시를 무효화**한다. (include_edges 활용)
- **IDX-16** 인덱스 빌드 명령을 제공한다: `python -m indexer build` (전체), `python -m indexer update` (증분), `python -m indexer status` (상태 조회).

## 4. Phase 2: Execution 요구사항

### 4.1 파일 선택 (UI)
- **EXE-01** UI에서 검증 대상 `.cpp` 파일을 선택할 수 있어야 한다 (파일 탐색기 또는 경로 입력).
- **EXE-02** 선택 시 인덱스 상태(최신 여부)를 함께 표시한다. 인덱스가 오래된 헤더를 참조하면 경고를 표시한다.

### 4.2 사용 심볼 추출 (Step 2)
- **EXE-03** tree-sitter로 `.cpp` 를 파싱하여 다음을 추출한다.
  - 함수 호출 식별자
  - 타입 참조 (변수 선언, 캐스트, 템플릿 인자 포함)
  - 구조체 멤버 접근 대상 타입 (가능한 범위 내)
  - 매크로 사용 (전처리 전 텍스트 기준 식별자)
  - 전역 변수 참조
- **EXE-04** 같은 `.cpp` 내부에서 정의된 심볼(로컬 함수, 로컬 struct)은 **제외**한다.
- **EXE-05** 추출 결과는 `{symbol, kind, first_line}` 목록으로 생성한다.

### 4.3 Context 선별 (Step 3)
- **EXE-06** **1차: Symbol Store 정확 매칭**. 추출된 심볼명으로 역인덱스를 조회한다.
- **EXE-07** **2차: 벡터 검색 보완**. 1차에서 매칭되지 않은 심볼(오타, 네임스페이스 차이, 매크로로 생성된 이름 등)에 대해 벡터 검색(Top-K=5)을 수행한다. 검색 질의는 심볼명과 주변 코드 한 줄을 결합한다.
- **EXE-08** **3차: 의존 확장**. 선택된 청크의 `dependencies` 를 따라 최대 depth 2까지 추가 청크를 가져온다.
- **EXE-09** **고정 3~4개 제한을 두지 않는다.** 대신 아래 규칙을 따른다.
  - 토큰 예산 `CONTEXT_TOKEN_BUDGET` (기본 1,500 토큰, 설정 가능) 을 초과하지 않는다.
  - 우선순위: 정확 매칭 > 의존 확장 > 벡터 검색 결과 순서. 동급 내에서는 사용 빈도 순.
  - 예산 초과로 제외된 청크 목록은 리포트에 **"미포함 컨텍스트"** 로 표시한다.
  - 사유: 3~4개로 고정하면 필수 정의가 누락되어 LLM이 추측(환각)하게 되므로, 예산 기반 선별로 누락을 줄인다.
- **EXE-10** 선별 결과(포함된 chunk_id, 선택 이유: exact/dep/vector)를 로그와 UI에 남긴다.

### 4.4 프롬프트 구성 (Step 4)
- **EXE-11** 프롬프트는 다음 순서로 구성한다. 고정 부분을 앞에 두어 Ollama의 KV 캐시 재사용을 돕는다.
  1. 시스템 지시 (고정 템플릿: 역할, 출력 형식, 금지 사항)
  2. Context 블록 (선별된 헤더·구조체·매크로, `// [file:line]` 주석 포함)
  3. 검증 대상 `.cpp` 코드 (라인 번호 부여)
  4. 검증 요청 (체크 항목 목록)
- **EXE-12** 시스템 지시에 다음을 명시한다.
  - "제공되지 않은 심볼에 대해 추측하지 말 것"
  - "모든 지적은 라인 번호와 근거 심볼을 포함할 것"
  - "확신이 없으면 confidence 를 low 로 표시할 것"
- **EXE-13** `.cpp` 파일이 큰 경우(예: 1,500줄 초과) **함수 단위로 분할하여 각각 검증**한다. 분할 단위마다 Context를 재선별한다.

### 4.5 LLM 호출
- **EXE-14** 모든 호출은 보안 게이트웨이의 `POST /v1/chat` 을 경유한다. 직접 Ollama 호출은 금지한다.
- **EXE-15** 기본 모델은 `qwen-coder` (Qwen 7B 계열, Q4_K_M 양자화)로 설정하고, UI에서 모델 변경을 허용한다 (게이트웨이 권한 정책 적용).
- **EXE-16** 응답은 스트리밍으로 받아 UI에 점진적으로 표시한다 (체감 속도 개선).
- **EXE-17** 출력 형식은 JSON으로 강제한다.

```json
{
  "findings": [
    {
      "severity": "high | medium | low",
      "line": 123,
      "symbol": "ATM_DEV_STATUS",
      "description": "구조체 필드 접근 전 NULL 검사 누락",
      "evidence": "dev->status 접근 (line 123)",
      "confidence": "high | medium | low"
    }
  ],
  "unverified_notes": ["..."]
}
```

### 4.6 후검증 (Post-validation) — 환각 억제 핵심
- **EXE-18** LLM 응답 파싱 후 다음을 자동 검사한다.
  - `line` 번호가 실제 `.cpp` 파일 범위 내에 있는지
  - `symbol` 이 검증 대상 코드 또는 제공된 Context 에 실제 존재하는지
  - `evidence` 문자열이 해당 라인 근처 원문에 포함되는지 (공백 정규화 후 비교)
- **EXE-19** 검사를 통과하지 못한 항목은 **"검증 불가(Unverified)"** 로 분류하여 별도 표시한다. 삭제하지 않는다 (사람이 판단할 수 있도록 남긴다).
- **EXE-20** JSON 파싱 실패 시 1회 재요청하고, 재실패 시 원문 응답을 그대로 UI에 표시한다.

### 4.7 UI 리포트 (Step 5)
- **EXE-21** 리포트 구성
  - 파일 정보 (경로, 줄 수, 검증 소요 시간, 사용 모델)
  - 지적 사항 목록 (심각도 순 정렬, 라인 클릭 시 코드 위치 이동)
  - 검증 불가 항목 (별도 섹션)
  - 사용된 Context 목록 (파일 경로, 라인 범위, 선택 이유) — 근거 투명성 확보
  - 미포함 Context 목록 (예산 초과로 제외된 항목)
- **EXE-22** 리포트는 Markdown 또는 HTML로 내보내기 기능을 제공한다.
- **EXE-23** 리포트에 "LLM 보조 검증 결과이며 최종 판단은 개발자가 한다"는 문구를 고정 표시한다.

## 5. 성능 개선 요구사항 (LLM 속도 대응)

속도 개선은 검색 자체보다 **LLM 입력 길이와 모델 설정**이 핵심이다. 다음을 적용한다.

- **PERF-01** Context 예산(EXE-09)을 통해 입력 토큰을 제한한다.
- **PERF-02** Ollama 설정
  - `keep_alive` 를 길게 설정하여 모델 언로드 방지 (예: 30m)
  - `num_ctx` 는 실제 필요 길이(예: 4096~8192)로 제한
  - `num_predict` 로 출력 토큰 상한 설정 (예: 1024)
- **PERF-03** 모델은 Q4_K_M 양자화 버전을 사용하고, 동일 GPU에서 `OLLAMA_NUM_PARALLEL` 을 조정한다.
- **PERF-04** 고정 시스템 지시를 프롬프트 앞부분에 배치하여 KV 캐시 prefix 재사용을 유도한다.
- **PERF-05** 같은 헤더 집합을 공유하는 연속 검증 요청에서는 Context 선별 결과를 캐시한다 (헤더 해시 기준 무효화).
- **PERF-06** 벤치마크 스크립트를 제공하여 파일 크기별(300 / 1,000 / 3,000줄) 단계별 소요 시간(파싱, 검색, LLM, 후검증)을 측정한다.

## 6. 보안 및 감사 요구사항

- **SEC-01** 모든 LLM 호출은 게이트웨이의 인증·단말·승인·모델 권한 검사를 통과해야 한다 (기존 요건서 FR-1~FR-4 준수).
- **SEC-02** 감사 로그(`access.log`)에 다음 필드를 추가한다.
  - `target_file`: 검증 대상 `.cpp` 경로
  - `context_chunk_count`: 포함된 Context 청크 수
  - `context_token_count`: Context 토큰 수
  - `unverified_count`: 후검증 실패 항목 수
- **SEC-03** 인덱스 DB(FAISS/Chroma, SQLite)는 사내 서비스 계정만 읽기 가능하도록 권한을 설정한다.
- **SEC-04** 인덱스에 포함된 원본 헤더 텍스트는 사내 소스코드이므로 외부 전송을 금지한다. 임베딩 모델 역시 로컬 실행만 허용한다.

## 7. 수용 테스트 (Acceptance Criteria)

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| AC-01 | 헤더 100개 대상 `index build` 실행 | 완료 후 벡터 DB·Symbol DB 생성, 재기동 시 재인덱싱 없음 |

| AC-05 | 오타·네임스페이스 차이 심볼 | 2차 벡터 검색으로 보완 매칭 |

## 8. 리스크 및 결정 필요 사항

| ID | 리스크 | 대응 |
|---|---|---|
| R-1 | 전처리기 분기(`#ifdef`)에 따라 실제 빌드와 다른 구조체가 선택될 수 있음 | `compile_commands.json` 연동, 미정의 분기는 양쪽 인덱싱 |
| R-2 | 매크로로 생성되는 심볼은 정적 파싱으로 찾기 어려움 | 2차 벡터 검색 + 미해결 심볼 목록을 리포트에 표시 |
| R-3 | 0.1초 목표는 벡터 검색 단독 기준이며, 전체 검증 시간은 LLM에 좌우됨 | 성능 목표를 단계별로 분리 측정 (PERF-06) |
| R-4 | "환각 없음"은 LLM 단독으로 보장할 수 없음 | 후검증(EXE-18~19)으로 근거 불일치 항목을 자동 분리, 면책 문구 고정 |
| R-5 | 7B 모델의 C/C++ 분석 정확도 한계 | 벤치마크 세트(알려진 버그 샘플)로 정확도 측정 후 모델 선택 확정 |
| R-6 | 레거시 코드의 포인터·메모리 관련 복잡한 의존 | 의존 depth 제한 + 예산 초과 시 명시적 미포함 표시 |

### 결정 필요 사항
1. 벡터 저장소: FAISS(단일 서버, 단순) vs Chroma(영구 저장 편의)
2. 임베딩 모델: bge-m3 vs multilingual-e5-base (벤치마크 후 결정)
3. 기본 LLM: Qwen 7B 계열 중 코더 특화 모델 채택 여부 및 양자화 수준
4. 빌드 정의 소스: `compile_commands.json` 사용 가능 여부 확인
5. Context 토큰 예산 기본값(1,500 토큰)의 적정성 (벤치마크 후 조정)

## 11. 용어 정의

| 용어 | 정의 |
|---|---|
| Semantic Chunk | 심볼 1개 단위의 의미 있는 코드 조각 (매크로, struct 등) |
| Symbol Store | 심볼명으로 청크를 즉시 찾는 역인덱스 (SQLite) |
| Context Injection | 검증에 필요한 정의만 골라 프롬프트에 주입하는 방식 |
| 후검증 | LLM 출력의 라인·심볼·근거를 실제 코드와 대조하는 자동 검사 |
| 검증 불가(Unverified) | 후검증을 통과하지 못해 근거가 확인되지 않은 지적 |
