2) 커서(Cursor)에 전달할 추가 검증 및 고도화 요구사항
아래 박스 안의 내용을 복사해서 커서 채팅창에 그대로 붙여넣으세요.

현재 만들어진 C++ 메모리 버그 분석기에 대해 다음 6가지 실무 요구사항이 제대로 반영되어 있는지 코드를 검증하고, 누락된 부분을 모두 수정해 줘. (원본 파일 보존은 필요 없고 오직 정확한 리포트 추출만 목적이야.)

1. 인코딩 강제 정규화 (EUC-KR  CP949 완벽 대응)

구형 VS 2008 CC++ 파일은 대부분 ANSI(CP949) 인코딩이야.

임시 파일을 읽을 때 utf-8 - cp949 - euc-kr 순서로 디코딩을 시도하고, 실패하는 특수문자는 errors='replace'로 무시해서라도 무조건 텍스트를 읽어내도록 파일 로더를 수정해 줘.

2. 줄 번호 하드코딩 전처리 (Line Number Injection)

LLM은 줄 번호를 직접 세지 못해. LLM에 코드를 넘기기 전에 파이썬이 임시 파일의 모든 줄 앞에 [L0001] , [L0002]  형태로 실제 줄 번호를 텍스트로 박아 넣은 뒤 넘기게 해 줘. (단, cppcheck에는 줄 번호가 안 붙은 원본 형태의 임시 파일을 넘겨야 해.)

3. 레거시 C 스타일 메모리문자열 함수 집중 타겟팅

현대적인 stdunique_ptr가 아니라 구형 C 스타일 메모리 조작을 잡아야 해.

malloc, calloc, realloc, free, new, delete, memcpy, memset, strcpy, strncpy, sprintf, _snprintf가 포함된 함수를 우선 추출해서 검사하도록 필터를 강화해 줘.

특히 배열 인덱스에 음수나 범위 초과가 들어가는 경우, strncpy 후 널 종료 문자(0) 누락, 조건문(ifelse) 분기에서 조기 리턴(return) 시 메모리 미해제(Leak)를 중점적으로 보도록 시스템 프롬프트에 명시해 줘.

4. 함수 단위 쪼개기 (Function-level Chunking)

수천 줄짜리 .cpp 파일을 한 번에 올라마에 던지면 컨텍스트가 넘치고 분석 속도가 너무 느려져.

파이썬에서 중괄호({ }) 짝 맞추기나 정규식을 이용해 함수 단위(또는 최대 150줄 단위)로 쪼개서 올라마에 순차적으로 요청하고, 진행률(Progress Bar)을 화면에 표시해 줘.

5. 리포트 출력 항목에 '문제 코드 스니펫'과 '수정 제안 코드' 추가

내가 리포트만 보고 바로 본 코드에 반영할 수 있도록 결과 출력 항목을 다음 구조로 고정해 줘.

파일명  정확한 줄 번호  함수명  버그 종류  확신도(HighMediumLow)

현재 코드 (Before) 문제가 된 해당 줄과 전후 2~3줄 코드

수정 방향 및 제안 코드 (After) 어떻게 고쳐야 하는지 짧은 1~2줄 코드 예시와 근거

6. 리포트 파일 자동 저장 기능 (Markdown  CSV)

Streamlit 화면에서만 보고 끝나는 게 아니라, 분석이 끝나면 결과 리포트를 날짜_시간이 찍힌 마크다운(.md) 또는 엑셀에서 열 수 있는 .csv 파일로 다운로드하거나 폴더에 자동 저장하는 버튼을 추가해 줘.

어차피 분석용 임시 데이터이므로 파이썬이 코드 텍스트 자체에 줄 번호를 글자로 박아서 LLM에 넘기면, 7B 모델이라도 줄 번호 오차율이 0%로 수렴합니다. 리포트만 보고 원본 코드에서 Ctrl + G(줄 이동)로 찾아가실 때 가장 중요한 장치입니다.

조기 리턴(return) 시 메모리 누수 타겟팅 (3번 항목)
금융단말기 레거시 코드에서 가장 많이 터지는 메모리 버그가 함수 상단에서 new나 malloc을 해놓고, 중간에 계좌 오류나 통신 에러 예외 처리(if (err) return FALSE;)로 빠져나가면서 해제를 깜빡하는 패턴입니다. 이걸 콕 집어 프롬프트에 넣어두면 기가 막히게 찾아냅니다.
