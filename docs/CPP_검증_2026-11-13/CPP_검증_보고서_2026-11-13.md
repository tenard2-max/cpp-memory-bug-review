## 1. 결론 요약

저장소에 자체 단위 테스트는 없다. `cli.py`는 Ollama가 없으면 `ReviewError`로 끝나고, 정적 결과만 보여 주는 폴백이 없다.

비LLM 정적 경로(프로젝트의 `run_cppcheck` 필터 + `suspects.py`)는 준비한 버그 사례 15건 중 **11건을 맞혔고**(재현율 약 73%), 정상 코드 2건은 오탐이 없었다. 같은 입력을 cppcheck·clang-tidy·ASan과 비교하면, 프로젝트 정적 경로가 **포인터 `sizeof` 오용**(suspects)은 잘 잡지만, cppcheck가 찾은 **지역 변수 참조 반환(`returnReference`)** 은 메모리 필터에서 빠져 놓친다.

Ollama를 모의(빈 findings)로 붙인 `review_paths`는 cppcheck 경고를 결과 목록에 **병합하지 않는다**. suspects(memset/sprintf)만 남는다. 그 결과 use-after-free 샘플을 UI에서 검토하면 cppcheck expander에는 `deallocuse`가 있는데도 화면은 **「보고할 메모리 버그와 초기화 버그가 없습니다 / 발견 0건」** 이라고 말한다. 이는 정확성 P0이다.

Linux에서 Streamlit은 `gpu_meter.py:108`의 `@ctypes.WINFUNCTYPE` 때문에 **임포트 단계에서 전체 화면이 죽는다**. UI 나머지 흐름은 테스트 전용 ctypes 심만 씌운 뒤에 확인했다. 원본은 고치지 않았다.

## 2. 비교 대상으로 고른 오픈소스 3개

이 도구의 목적(C/C++ 메모리·초기화 버그 탐지)과 이미 코드에 있는 `.clang-tidy`·cppcheck 연동을 기준으로 골랐다.

| 선정 | 저장소 | 선정 이유 | 이 도구와의 접점 |
| --- | --- | --- | --- |
| 1 | [danmar/cppcheck](https://github.com/danmar/cppcheck) | 빌드 DB 없이 파일 단위로 누수·이중 해제·UAF·미초기화를 잡는 정적 분석기. 프로젝트가 1차 필터로 이미 사용한다. | `analyzer.py`가 XML을 파싱한 뒤 `MEMORY_IDS`/`MEMORY_WORDS`로 걸러 LLM 힌트로만 넘긴다. 결과 목록으로 자동 병합하지는 않는다. `returnReference`, `pointerSize`는 필터에서 빠진다. |

| 3 | [google/sanitizers](https://github.com/google/sanitizers) (AddressSanitizer, GCC/Clang `-fsanitize=address`) | 실행 시 누수·UAF·이중 해제·버퍼 넘침·new/delete 불일치를 확정하는 런타임 기준. | 이 검토기는 실행·계측을 하지 않는다. ASan은 함수가 실제로 호출될 때만 잡으며, 미초기화 읽기는 ASan 범위가 아니다(MemorySanitizer/Valgrind 영역). |

## 4. 탐지 차분 표

동일 입력:

- 프로젝트 샘플 `samples/use_after_free.cpp`(P01)
- `bug_samples.json` 6건을 함수로 감싼 파일(S01–S06)
- 알려진 사례 K01–K08(누수, 이중 해제, UAF, 버퍼 넘침, 미초기화 읽기, new/delete[] 불일치, 댕글링 참조, 포인터 sizeof)과 정상 코드 N01–N02

판정: 기대 버그 종류와 도구가 낸 종류가 겹치면 TP, 버그 파일에서 미검출이면 FN, 정상 파일에서 경고면 FP, 정상을 조용히 통과하면 TN. cppcheck 열은 **프로젝트와 같은 메모리 필터**를 기준으로 다시 세었다(style의 unusedStructMember 등은 오탐으로 세지 않음).

「프로젝트 정적」= `run_cppcheck` + `suspects`(memset/sprintf). 「프로젝트+모의 LLM」= `review_paths` + 빈 findings 모의 Ollama(교차검증·문장정리 끔).

요약 (S06을 버그 사례에 넣으면 정적 재현율은 더 낮아진다. 위 버그 15건 기준, S06 포함 시 프로젝트 정적 TP 11 / FN 4):

- 프로젝트 정적: TP 11, FN 4(K07, S02, S04, S06), FP 0, TN 2. 재현율 약 73%.
- 프로젝트+모의 LLM: TP 4(전부 suspects 패턴), FN 11, FP 0. **cppcheck로 이미 잡힌 UAF·누수·이중 해제·미초기화가 결과에서 사라진다.**
- clang-tidy(`.clang-tidy`): 핵심 메모리 버그는 대체로 TP, S02/S04는 미검출.
- ASan: 실제로 `main`이 버그 경로를 실행한 사례는 잘 잡는다. 미초기화 읽기와 “아직 호출되지 않은 함수 안의 버그”, 비충돌 sizeof 오용은 한계다.

추가 관찰:

- `suspects.py`의 확정 패턴(포인터 `sizeof(p)`, 스택 `sprintf` 길이 초과)은 참조 도구보다 이 프로젝트에 유리하다.
- 구조체 부분 미초기화·strncpy 널 누락은 정적 경로가 거의 못 잡으며, 문서상 LLM few-shot(`bug_samples.json`)에 의존한다. 모의 LLM은 빈 답이라 이번 측정에서는 FN이다.
- `chunks.py`의 `MEMORY_CALL`에는 malloc/free/new/delete가 들어 있어 UAF 샘플은 청킹 대상이 된다. 문제는 청킹이 아니라 **결과 병합**이다.
